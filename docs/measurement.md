# Measuring the method, not the demo

This is a protocol for evaluating the runnable v0.3 [generic method runtime](methods.md) and a future source-to-learning method built on it. **No comparative results are reported here.** The [existing systems benchmark](benchmarks.md) measures synthetic cached-job scheduling on one machine, and method runtime tests check DAG execution and cache behavior. The [evaluation plan](evaluation.md) separates parser, source, semantic, learner and delivery claims. None proves this runtime improves teaching or beats another product.

## Freeze the task before running it

Recruit a small public or permissioned source collection **not used to design the method**. Include prose, a table, a figure, a scanned or difficult page, overlapping sources, one conflict, and at least one assessable omission risk. Choose a real production brief: named learner, deadline, intended output forms, allowed source roles, quality rubric, and delivery surface. Use a source-region inventory drawn from rendered originals, then have two qualified reviewers independently mark important answer objects, qualifiers, visual dependencies, task priority and acceptable deliberate omissions. Resolve disagreements and retain both initial labels. This reference set is imperfect; publish its uncertainty and the adjudication rules.

Separate teaching material, style exemplars, and held-out evaluation questions. If question examples are allowed to shape form, give all compared systems the same examples and exclude the held-out items from generation. Check for near-duplicate leakage. Freeze corpus hashes, task brief, method and adapter revisions, model IDs, budgets, concurrency/rate limits, operator instructions, and acceptance criteria before the comparison. The exact rules can differ by task but must not change after seeing which product produced a better result.

## Compare completed journeys

Use at least three baselines on the same brief where feasible: a careful human-assisted source-order workflow, Lamina's current fixed pipeline, and the proposed method runtime. A Manus or NotebookLM comparison can be added when accounts and lawful source use are available; treat each as the full documented product with a capable operator. A LangGraph comparison means a built workflow with its implementation time counted separately. Match the content scope and target deliverables. Keep the model/provider equal for Lamina's internal A/B when isolating the runtime. For cross-product tests where models cannot be matched, report the combined system result, not a causal runtime advantage.

Perform several paired runs across different source sets and task types, with run order rotated where possible. Record first-draft time and **time to accepted, accessible artifact** separately. Include the operator's setup, inspection, correction, media QA, and delivery. A polished file that cannot be found or opened on the intended device has not met the delivery endpoint. Do not exclude failed runs or timeout attempts from the latency distribution. Report median, 90th percentile, range and raw run count; small samples do not justify precise tail forecasts.

## Score quality at the right denominator

| Measure | Denominator and evidence | What it does not prove |
| --- | --- | --- |
| Source-region coverage | Human-inventoried text, tables, figures and scanned regions: usable capture or explicit unsupported status | Understanding of captured material |
| Important-object recall | Adjudicated task-relevant answer objects: accurately represented, deliberately omitted with accepted reason, missed, or wrong | That every possible fact was inventoried |
| Qualifier and contrast preservation | Labeled numbers, conditions, exceptions, opposed alternatives and conflicting sources | Learner retention |
| Grounding | Independently checked artifact claims against cited original region, labelled supported, contradicted or unestablished | Source truth outside the task corpus |
| Retrieval quality | Blinded reviewers judge whether prompts elicit specified answer objects and discriminate near alternatives; where possible, learners answer after a delay | General learning efficacy from a single task |
| Editorial usability | A new operator locates a seeded omission, explains why it occurred, repairs it and identifies the revised delivered file | Universal UI preference |
| Delivery | Exact file hash or URL, open/play check on target surface, media QA if applicable | That the learner consumed it |

Report false merges and missing required objects individually, even if aggregate coverage looks good. Have reviewers judge artifacts blind to product label where practical. A safety-critical error or a missing central answer can fail acceptance under a predeclared rule even if the average score is high. Do not let structural validation, citation count, page count, or a model's `pass` response stand in for these judgments.

## Instrument the run

For every node, record its version, dependency IDs, input and output digests, resource lane, queue-entry/start/end times, service time, cache hit/miss, attempt and retry count, error, and downstream invalidations. The current method receipt already records node status, lane, dependencies, serialized request bytes, wall time and output digest or error; queue timing, token use, costs, retries and invalidation statistics require added instrumentation. For semantic calls record observed input/output tokens if the provider reports them, model and revision, request size and provider-reported charges. If token or price data is absent, mark it **estimated** with the tokenizer and posted rate used; never combine observed and estimated costs into one unlabeled number. Record local CPU/GPU time, storage peaks, network transfer, human minutes and any external subscription/credit unit separately. A cached run still has verification and retrieval work; it is not zero-cost output.

Measure total input-token amplification `A = Σ input tokens / distinct accepted source-text tokens`, by stage as well as overall. Report the maximum request and whether it exceeded a chosen context or payload limit. Interpret high `A` carefully: repeated context can improve boundary interpretation, while excess duplication can waste cost. Measure service work `W = Σ t_i`, longest dependency path `D`, lane work `W_r` and lane capacity `c_r`. Bounds `T ≥ max(D, max_r W_r/c_r)` locate structural ceilings; they do not predict wall time under varying latency, rate limits, queue contention, retries or human waits. Report actual time against the bound and explain the gap rather than claiming an ideal speedup.

Seed at least two review observations after a first output: a local wording/format defect and a missing concept that should alter the global route. Record the nodes reopened, re-executed service cost, human repair time, artifact versions replaced, and any stale reviewer verdict. Define failure locality as affected work divided by total relevant work, but inspect whether a small repair scope incorrectly skipped a dependency. Also force a worker interruption and resume from durable state; verify stale completions do not publish and cached outputs still match their semantic inputs. These are separate recovery and correctness tests.

For queues, log arrivals, service-time distribution, active capacity, API throttles, and wait-time percentiles by resource lane. Apply a queue model only if its assumptions fit the observed workload; batch arrivals, correlated long model calls and shared account rate limits can invalidate simple steady-state formulas. Compare worker widths only at similar output quality and source scope. More concurrent jobs can increase retries or review burden, so the relevant frontier is **cost and time per accepted artifact**, not drafts per minute.

## Test transfer, not just replay

Save the method/procedure and start a fresh agent or operator without the original conversation. Give them a new source collection and the same task class. Observe whether they choose the right source policy, construct sensible dependencies, identify task-specific answer objects, and apply the prior method only where it fits. Include a counterexample in which the previously preferred teaching form is wrong. If a later method revision is proposed from user feedback, compare old and new versions on held-out cases; retain both, document losses as well as gains, and require explicit acceptance before promotion. Reusing a prompt or caching a response is not evidence of learned method improvement.

Publish the exact test corpus or a lawful reproducible substitute, task briefs, evaluation labels and disagreements, runtime traces with sensitive content removed, failures, costs, and artifact hashes. State separately what was wired, what passed structural tests, what reviewers accepted, what learners used, and what remains untested. A stronger competitive claim is warranted only after repeated quality-matched comparisons support it.
