# Design constraints for a reusable method runtime

This note carries lessons from the original Tintinalli/ROUNDS production history into Lamina's broader work. That history is private. It motivates the constraints below, but the public product and examples must use original or permissioned sources rather than copy private conversations, medical decks, or exam papers. Lamina v0.3 already runs bounded method DAGs with resource lanes, per-node cache and local observations; most editorial and learning requirements below remain design goals. See [methods](methods.md) for the runnable contract, [architecture](architecture.md) for the source-to-lesson path, and [measurement](measurement.md) for the proposed tests.

## The decision worth preserving

A source-to-artifact system has to decide what the source says, what matters for this task, what deserves its own treatment, what can be grouped, what requires a different teaching form, and what remains unaddressed. The hardest failure in the historical work was a polished artifact that looked complete while an important item was absent or badly taught. A correct citation and a processed-page count could coexist with that failure.

Lamina should retain a visible chain from **source region → candidate claim or answer object → editorial decision → artifact section or deliberate omission → review observation → repair → delivered version**. Each arrow needs an owner and a check appropriate to its claim. The user should be able to ask, in ordinary language, “What did this come from? What was left out? Why? Which version did I actually receive?”

## Constraints on methods

1. **The source policy belongs to the task.** A teaching source, a style exemplar, a conflicting reference, and a held-out evaluation item have different roles. A prior exam question may teach the format or supply an answer inventory, yet it may need to stay out of prompts for a fair held-out test. The method must declare the role and allowed uses before ingestion. One permanent teaching-versus-assessment flag cannot express every legitimate task. The policy must also say what to do when a table, image, scan, or attachment is unreadable; a text digest does not establish visual coverage.

2. **The learning representation should preserve objects, not just topic names.** A source can mention a procedure without describing its steps, or mention a nomogram without teaching the decision it supports. For a chosen task, the method should inventory answer atoms, conditions, quantities, visual dependencies, source conflicts, and expected retrieval operations. It should retain both the source wording and the model's interpretation so an editor can catch a missing qualifier. A universal “atomic” segmentation rule is not assumed: the unit may be a single marked answer, a decision boundary, an image comparison, or a larger causal model.

3. **Editorial selection is explicit and reversible.** The system can propose importance from source evidence, prerequisites, consequence of omission, and task examples. It must record inclusion, deferral, exclusion, uncertainty, and the reason. Search score is relevance to a query, not priority. An editor must be able to reverse a decision without discarding unaffected reading and authoring work. A model prior can suggest a likely omission; it cannot silently become an attributed source fact.

4. **Teaching form follows the object and learner.** Some content needs a list rehearsed accurately; some needs a contrast, changed-case decision, annotated image, worked calculation, compact reference, or long-form audio. A single lesson template should not force all of them into three generic questions. The method can select among forms, show the reason, and check whether a learner can retrieve the particular object after attention has moved on. Audio needs its own pacing, spoken clarity, script-to-file check, and actual playback verification if audio is produced. A speakable script alone is a script.

5. **The work graph expresses dependencies.** Parallel readers are useful when source regions or topics can be examined independently. A bridge review is needed when distinctions cross partitions. An editor may need all relevant evidence before deciding a shared curriculum route. Model review, human review, media generation, and delivery need separate dependencies. The v0.3 runtime provides a validated DAG, bounded JSON jobs, declared dependency results, resource lanes and per-node cache identity. Task-specific source policy, typed output checks, review and delivery gates still need to be built on it. That is more useful than treating “workers = 8” as the whole parallelism design. A graph can still have a long serial path; more workers cannot remove it.

6. **Context is a finite resource, not free coordination.** Each worker should receive enough local source and neighboring context to interpret its assignment, plus a compact shared board where needed. Record the bytes and tokens sent, the largest request, repeated context, and any omitted material. Do not assume that a global prompt scales to a book merely because local readers run in parallel. A compact board is only safe if source pointers allow a reviewer to reopen the original passage before making consequential merges or omissions.

7. **A review observation must identify repair scope.** A reviewer should name a wrong assertion, missing answer object, misleading grouping, unreadable figure, unsuitable retrieval prompt, or delivery defect and attach it to the exact artifact version. The method then identifies the smallest affected descendants in the job graph. It should not rerun every stage for a local wording error or leave a global curriculum decision untouched after a missing central concept is found. A passing model review is a stated rubric response, not independent truth. High-stakes material requires qualified review appropriate to the domain.

8. **Recovery and delivery are part of the method.** Jobs need durable status, bounded retry, idempotent publication, stale-owner protection, and visible errors. External delivery needs a receipt: target, artifact digest, timestamp, verified accessible link or file, and any failed check. “Generated,” “uploaded,” “available on a phone,” and “used by the learner” are different states. The public example need not include cloud audio; it must still make the boundary clear.

9. **A method changes only on evidence.** A procedure can be reused today, but the proposed method runtime does not thereby learn. A reusable revision needs a concrete observation, a proposed change to representation or execution, a new version/cache identity, a comparison on held-out tasks, and acceptance or rejection. Keep the old version and counterexample. User observations can reopen decisions; they are not automatically ground truth or a license to overwrite the method.

10. **The product should show its work where a user can act.** The source and coverage views should answer which files, regions, cards or question examples were accepted; what artifact each item influenced; what was deferred; what is awaiting review; and what finished file the user can open. Show enough detail to repair a gap without forcing a reader to inspect logs. Any public claim of “complete” must name its denominator and exclusions.

## A plausible first connected implementation

The generic runtime now provides bounded JSON jobs and resource lanes, a dependency graph, per-node cache/recovery, and separately recorded operator observations. A method node can explicitly name same-family observation IDs and receive those records as reference data; the observations **do not** reopen work automatically. An operator selects the observation in the method and reruns it. A concrete learning method could use that machinery for source reading, candidate inventory, editorial selection, authoring, review and export. This sequence preserves a general runtime while giving it a demanding real task. It does **not** require making a medical exam engine, an Acrobat extension, an audio host, or an autonomous learning system the first milestone.

One public, permissioned corpus with prose, a table, a figure, and related questions would expose the crucial decisions. Freeze a source-region inventory before generation. Have qualified reviewers label important answer objects, explicit omissions, source conflicts and unsupported claims. Build a route and at least two different output forms from the same governed representation. Insert a missing-item objection after first review, repair it, and show exactly which jobs and artifacts changed. The product test is whether an unfamiliar user can locate and correct the omission, then find the delivered revision. The technical test is whether this happens with less avoidable context and rework at comparable quality and measured cost.

## Cost model for design, not a speed promise

For a graph with jobs `i`, let `t_i` be an observed service time and `W = Σ t_i` total service work. Let `D` be the sum of service times on the longest dependency path. With `p` otherwise identical available workers, `T ≥ max(W/p, D)` is a lower bound, not a prediction. With resource lanes `r` (for example model-call concurrency, CPU parsing, GPU audio, human review), a stronger bound is `T ≥ max(D, max_r W_r/c_r)`, where `W_r` is service time demanded from lane `r` and `c_r` is its capacity. Shared API rate limits, setup, scheduling, retries, and external latency add time. If one job needs several resources at once, the lane bound alone is incomplete.

Context amplification can be reported as `A = (Σ input tokens across semantic jobs)/(tokens in distinct accepted source text)`. It includes repeated instructions and summaries, so it describes request burden, not semantic inefficiency by itself. Report the numerator by stage, the maximum single request, and the share of source regions never sent in usable form. For repair, measure `R(o) = Σ service cost of jobs invalidated by observation o`, plus reviewer time and delivery replacement. A good graph lowers `R` for local defects without hiding global dependencies. These formulas are accounting devices; scheduling quality and teaching quality require observed outcomes.

Queueing estimates need measured arrival rates, service distributions, concurrency limits, and throttling behavior. Near saturation, small service-time changes can have large effects on wait time; no fixed “20 agents equals 20 times faster” claim follows. Report median and tail time to an **accepted and accessible** artifact, alongside its quality and cost. [The existing synthetic systems benchmark](benchmarks.md) exercises only cached SQLite jobs and declared sleeps, so it cannot establish model, reviewer or delivery performance.
