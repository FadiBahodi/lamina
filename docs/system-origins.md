# Where Lamina's design problems came from

Lamina grew out of several kinds of document-generation work. The common difficulty was not making an LLM write. It was deciding what the source meant for a particular job, dividing that work without losing important detail, and checking the result in the form people actually use. The originating material and conversations are private; the mechanisms below are described through general examples.

A technical brief, a differential reference, a spoken lesson, and an interactive practice case ask different questions of the same source. A brief needs a defensible decision and a traceable argument. A differential reference needs a complete answer to a presenting problem without repeating the same question in several places. A spoken lesson needs an intelligible route, timed repetition, and playable audio. An interactive case needs facts that appear only when the candidate requests them, consequences of actions, and a separate examiner view. A single universal “lesson” schema cannot represent all four well.

An assessment question adds another boundary. A case setter may see a teaching map and design the full question sequence, while a candidate-solver used for quality checking should see only the information revealed up to the question it is answering. A marking guide belongs with the examiner, not the candidate. A changed question needs another blind solve and review; a repaired answer key alone does not establish that the question became answerable. The same source collection can support a study guide, rapid recall prompt, and full case, but each output needs its own information flow and acceptance test.

Several design constraints survived those projects:

Source roles often require more than a teaching-versus-test split. A current procedure can be factual authority, an older note can establish a conflict, a prior question can be an example of assessment form, and a protected question set can remain unseen for evaluation. The task owner must choose those roles. Discovering a file, considering it, using it as evidence, and holding it out are different events, each with a different claim about coverage.

| Problem seen in production | Mechanism worth carrying forward | Boundary that remains important |
| --- | --- | --- |
| Source pages, diagrams, lists, and tables were lost or mixed before writing began. | Preserve source identity, ordered regions, ownership of a focal region, neighboring context, and the role of each source. | A text extraction receipt does not establish that a figure or table was understood. |
| Closely related questions produced repeated answers, while blunt deduplication erased meaningful variants. | Give each retrieval task an owner. Record when two objects are the same task, related variants, or contrasts. | Recurrence of a fact in a new context can be useful; deleting repeated words is not semantic reconciliation. |
| Early selection made a later draft look coherent while important source ideas were absent. | Keep a path from the final claim or omission back to the broader source inventory and the selection decision. | Source consideration, editorial inclusion, teaching, and reader benefit are separate claims. Selective output can still be right. |
| Parallel writers duplicated explanations or missed dependencies. | Give them a common plan, evidence boundaries, explicit prerequisite results where needed, and resource limits. | A dependency graph schedules work; it does not by itself choose a good decomposition or make prose coherent. |
| A review found one wrong claim or missing answer, but a whole product was rerun. | Attach a finding to the affected artifact location, source object, and upstream decision; preserve unaffected work. | Applying a patch is not the same as verifying the corrected final output. |
| A structurally valid file was difficult to study, hear, or use in an interactive session. | Define acceptance at the delivered surface: page, audio player, or candidate/examiner interaction. | Rendering, navigation, citations, timing and content quality require different checks. |

These constraints support an architecture with a task contract, source policy, chosen intermediate representation, explicit worker context and dependencies, local repair, and artifact-specific delivery checks. They do not prescribe one pipeline for every task. Choosing a representation is the decisive step: a short explanatory document may need claims and conflicts; a diagnostic reference may need presentation-to-answer objects; an interactive case needs states, reveal conditions, and marking actions.

Today's Lamina has three related paths. The earlier source-to-guide builder ingests text with stable source IDs and locations, extracts ideas with adjacent context, reconciles them, plans lessons, authors them, and gates export on review. The source-aware production path reads owned text windows under operator-assigned source roles, asks a model to choose a section representation and grouping for the brief, gives parallel writers a shared route and exact evidence, and can repair one flagged section and recheck it. For guides and assessments, an optional retrieval-target stage gives each extracted idea one question or use-context owner and preserves exact cited answer items before writers begin; model judgment still decides equivalence and variants. A named section revision reuses unaffected cached work; the local Projects interface and CLI use this engine. Assessment runs then test the candidate-facing questions through blind answers and separate key-and-evidence judgments. A configured local speech adapter can render a ready podcast script to a checked PCM WAV and synthesis-input transcript. The general method path runs an operator-declared graph with selected task fields, direct dependency outputs, resource lanes, caching, receipts, and optionally selected prior observations. These are distinct working contracts. Production does not yet infer all semantic dependencies between finished sections or route a missing source idea back through extraction and planning. It does not interpret arbitrary figures, administer an interactive case, listen to rendered audio, or verify its spoken fidelity. Generic method nodes do not inherit production's source checks.

Progress should be demonstrated on a new task, not inferred from architecture alone. A credible test would show the source roles and chosen answer objects, inspect what each worker received, expose a deliberate conflict or omission, repair only the affected dependency path, and compare the final artifact at matched scope and quality. A cache hit, source-link count, or passing schema check is useful evidence about one boundary, not a verdict on the whole result.
